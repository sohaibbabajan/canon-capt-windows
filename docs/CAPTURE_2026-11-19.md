# First Surface identity capture and 0.1.1 fix

User-supplied reports, 2026-11-19 17:34 UTC (20:34 Baghdad), running diagnostic
0.1 on the Windows 11 ARM64 Surface. Printer reported `LBP6000/LBP6018`, USB
hardware IDs `USB\VID_04A9&PID_271A&REV_0100` and `USB\VID_04A9&PID_271A`;
service `usbprint`. Exact Windows build and firmware are not supplied. Identity
field `VER:3.0` is preserved without assuming it means firmware version.
Serial and device-instance paths are omitted here and from the test fixture.

Observed evidence:

* GUI worker self-check completed with exit code 0.
* SetupAPI enumerated the USB printer; exclusive open succeeded.
* `IOCTL_USBPRINT_GET_1284_ID` completed and reported 86 bytes, identically in
  both inspection and status modes. These are application-visible IOCTL bytes,
  not a USB bus trace.
* Version 0.1 rejected the identity length before any CAPT request, exiting 2.
  CAPT bidirectional status and printing have **not** been demonstrated.

The capture is preserved verbatim in
[`tests/fixtures/canon_271a_identity.hpp`](../tests/fixtures/canon_271a_identity.hpp).
The leading bytes are `56 56`: interpreted as a 16-bit length in either order,
they mean 22,102, inconsistent with the 86 returned bytes. Individually each is
86. The remaining 84 bytes are:

```text
MFG:Canon;MDL:LBP6000/LBP6018;CMD:CAPT;VER:3.0;CLS:PRINTER;DES:Canon LBP6000/LBP6018
```

There is no trailing semicolon or NUL. We do not know whether this representation
originates in the device, USBPRINT or another part of the stack. The
[Microsoft IOCTL documentation](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/usbprint/ni-usbprint-ioctl_usbprint_get_1284_id)
describes a two-byte size prefix; it does not document this duplicate-byte form.

## Deliberate, bounded exception

Version 0.1.1 chooses an explicit policy only when a complete SetupAPI hardware-ID
entry equals `USB\VID_04A9&PID_271A` (ASCII case insensitive). No substring,
serial/interface path or model-string-only match enables the policy.

The exceptional representation must have no NUL/padding, at most 255 returned
bytes, and **both prefix bytes equal to the entire returned size**. All bytes
after the prefix remain printable ASCII, all manufacturer/model/command fields
are unique and terminated, and the only accepted unterminated final field is
`DES:Canon LBP6000/LBP6018`. Manufacturer must normalize to `CANON`, model to
`LBP6000/LBP6018`, and command set to `CAPT`. Missing, duplicate, inconsistent
or truncated identity fields still fail. Ordinary strict decoding is unchanged.
The selected exception is printed explicitly in the diagnostic report.

Regression tests replay these exact bytes, exhaust all 65,536 prefix values,
reject every truncation (also with rewritten prefix bytes), reject control/NUL
injection, identity-field mutations and model/VID/PID lookalikes. Tests also
confirm strict callers reject the captured anomaly and the explicit policy
still accepts normal, correctly framed identities. This is a parser regression
fix, not evidence that 0.1.1 succeeds on the Surface.

## First successful CAPT status exchange

On 2026-11-19 at 17:41 UTC the user ran **Check Canon status** in 0.1.1 on
the same Surface. The user confirmed the paper tray was empty. The hardware
ID and the 86 identity bytes matched the earlier report. The diagnostic
accepted the identity, wrote `A8 A0 04 00`, received an echoed `A0A8` and
exited with code 0. The reply declared 92 bytes including its four-byte
header. The three application reads returned 6, 64 and 22 bytes.

Status word 0 was `0x8E33` and word 1 was zero. The reference decoder's first
paper-out bit was set and the second was clear. The reported processing bit
was set while the printing, busy and buffer-full flags were clear. The
decoding, received, out and completed counters were zero. This observation
associates the decoded paper-out flag with one confirmed empty-tray state.
A loaded-tray reading will test whether it clears under otherwise similar
conditions. The report records one status transaction. Physical page output
and spooler integration still require separate tests.
